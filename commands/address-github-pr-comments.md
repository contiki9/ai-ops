# GitHub PR コメントへの対応（Address GitHub PR Comments）

## 概要（Overview）

未対応のレビュー指摘を処理し、必要な修正を入れたうえで、**GitHub 上の該当レビューコメント（スレッド）に返信する**。チャット内に「返信文案」だけを残して終わらせない。

**成果物について**: レビュアーが PR 上で読む**返信コメント**は、特に指示がない限り**日本語**で書く。コミットハッシュやファイルパスなど、ツールが要求する表記は英語のままでよい。

**認証**: `gh auth status` で GitHub CLI がリポジトリに書き込める状態であること。書き込み不可の環境では、ユーザーに返信投稿を依頼し、チェックリストの該当項目を未完了のまま明示する。

## 手順（Steps）

1. **同期とコメントの洗い出し（Sync and audit comments）**
    - ブランチの最新変更を取り込む
    - PR の会話を開き、未解決のコメントをすべて読む
    - 影響ファイルやテーマごとにコメントをグループ化する
2. **対応方針の整理（Plan resolutions）**
    - スレッドごとに求められているコード変更を列挙する
    - 補足説明や追加コンテキストが必要なものを特定する
    - 実装前に依存関係やブロッカーがないかメモする
3. **修正の実装（Implement fixes）**
    - スレッド単位で、指摘に沿った変更を入れる
    - 影響の大きい変更のあとは関連テストやリンターを実行する
    - 対応した内容が分かるようにコミットする
4. **返信の投稿（GitHub）**
    - 各インライン／レビューコメントのスレッドに、実施した対応または判断理由を**その場に返信**する（チャット用の下書きだけにしない）
    - レビュアーが確認しやすいよう**コミット SHA**（短縮可）や必要なら permalink を書く
    - 残課題やフォローアップがあれば返信内で明示する
    - **API 例**（トップレベルのレビューコメント ID が分かっている場合）:  
      `gh api --method POST repos/<owner>/<repo>/pulls/<PR番号>/comments/<コメントID>/replies -f body='…'`
    - 会話タブへの一般コメントだけでは、インライン指摘が未対応に見えることがあるため、**指摘ごとのスレッド返信**を優先する

## 返信 チェックリスト

- [ ] **GitHub 上で、指摘ごとのレビューコメントに返信した**（または書き込み不可でユーザーへ依頼し、その旨を記録した）
- [ ] すべてのレビューコメントに言及した
- [ ] 必要なコード変更を実装し、テストした
- [ ] 微妙な議論には説明文を返信に含めた
- [ ] フォローアップは記録したかエスカレーションした
- [ ] レビュアー向けに PR の状態を更新した（再レビュー依頼など、運用に合わせる）
